# Phase 5, Step 3A — reusable settlement cycle design

**Status:** design for review; no schema, API, migration, or UI change has been implemented. This document describes a standalone-MongoDB-compatible proposal, not a guarantee that its future implementation has passed concurrency testing.

## 1. Problem and current implementation

A group currently acquires a permanent `financialHistoryAt` marker before its first shared expense. Its first settlement proposal sets the permanent `settlementStartedAt` marker; expense creation, replacement, and deletion then remain blocked forever. This protects financial history, but prevents a group from recording expenses for a later round of activity. A cycle must permit _new_ expenses without making an old frozen expense mutable or erasing a confirmed settlement.

The design is based on these current-code facts:

## 2. Proposed records and indexes

### GroupFinancialCycle

One document per group round:

| Field                                                        | Rule                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `_id`, `group`                                               | Immutable ObjectIds; IDs are allocated once and stored in the reservation before a multi-document transition.                                                                                                     |
| `sequence`, `previousCycleId`                                | Positive, monotonically increasing per group; immutable. Sequence 1 is the legacy/first cycle. No calendar meaning.                                                                                               |
| `currency`                                                   | Immutable `INR` initially, equal to group currency.                                                                                                                                                               |
| `status`                                                     | `open`, `frozen`, or `closed`; monotonic transition only.                                                                                                                                                         |
| `activeSlot`                                                 | True only for open/frozen documents; absent on closed documents. A partial unique index `{ group: 1 }` where `activeSlot: true` prevents two active cycles. Status/slot consistency needs a collection validator. |
| `memberIds`                                                  | Immutable, sorted membership snapshot at opening; stable user IDs, never names or emails. Expenses and settlements must use this snapshot.                                                                        |
| `createdAt`, `updatedAt`, `openedAt`, `frozenAt`, `closedAt` | Server UTC timestamps. Transition timestamps are set once and never moved backward.                                                                                                                               |
| `__v`                                                        | CAS version for cycle transitions and ETags.                                                                                                                                                                      |
| transition receipts                                          | Immutable fixed operation IDs for opening, freezing, and closing; optional closing integrity totals/digest. They allow a retried transition to identify its prior effect.                                         |

Use automatically numbered display labels (“Cycle 1”, “Cycle 2”). Do not ask users for dates or impose month boundaries. A later optional user label can be metadata; it must not determine identity or financial scope. A cycle with no expenses is valid and may be explicitly frozen and closed.

Add to `Group`: `currentCycleId`, `cycleEpoch`, `currentCycleState`, and `financialProtocolVersion`. The group pointer/state are the **write gate and recovery mirror**; the cycle document is the durable historical state. Outside a reservation they must agree. A temporary disagreement during a reserved operation is expected and must return `FINANCIAL_BUSY` until recovery. Keep `financialHistoryAt` permanently. Keep `settlementStartedAt` as _earliest-ever settlement start_ for legacy history, never as a global new-cycle write gate.

Extend `Group.financialOperation` with immutable `cycleId`, `cycleEpoch`, fixed target IDs, stable normalized payload/hash, expected versions, and phase `checking` or `applying`. Add operation kinds for explicit freeze, close, and open. The existing operation ID remains globally unique. Store the complete intent before touching another document. No TTL or timeout may delete an applying reservation.

Add immutable `cycleId` to every `GroupExpense` and `GroupSettlement`, including deleted-expense tombstones and old creation receipts. For new writes it is mandatory; legacy rows are backfilled before enabling the new protocol. Existing `group + creator/sender + creationKey` unique indexes remain unchanged so an old key cannot create in another cycle. Add `{ group: 1, cycleId: 1, expenseDate: -1, _id: -1 }` for cycle expense history and `{ group: 1, cycleId: 1, _id: -1 }` for cycle settlements. Keep existing group-wide history and receipt indexes. Add unique `{ group: 1, sequence: 1 }` on cycles, plus the active-slot unique index. A group-current pointer index is unnecessary for ID lookups.

Collection validators should enforce field shape, immutable IDs/associations where MongoDB can express them, valid status/slot and money representations. Cross-document balance, membership, and group/cycle coherence still require the serialized service protocol and reconciliation tests; do not imply a collection validator can enforce them alone.

## 3. Lifecycle and permissions

```text
No cycle --(first expense or explicit owner open)--> Open
Open --(first valid settlement proposal or explicit owner freeze)--> Frozen
Frozen --(owner close after reconciliation)--> Closed
Closed --(owner creates a new cycle)--> New Open cycle
```

There is at most one open **or frozen** cycle per group. Open accepts current-cycle expenses and expense corrections. The first capacity-valid settlement proposal reserves the group, durably freezes that cycle, then inserts its pending settlement. If the proposal is rejected, or remains pending, the cycle stays frozen. Withdrawal is not supported by the current API and is outside the initial cycle milestone; a later pending-only withdrawal would not reopen it. An owner may explicitly freeze an empty or nonempty cycle so it can be closed without a settlement proposal. Frozen accepts settlement proposals and recipient decisions, but no expense creation/edit/deletion. Closed accepts neither. Historical reads remain available to members.

Closing requires **all** member net balances in that cycle to be exactly zero, no pending settlement, no other financial operation, valid source data, and safe aggregate arithmetic. A zero-expense cycle closes with zero balances after explicit freeze. Rejected proposals contribute nothing to net balances or pending capacity and do not unblock expense editing. A pending proposal blocks closing even if its amount would eventually produce zero balances. There is no implicit debt forgiveness, carry-forward, or rollover. If people settle externally without recipient-confirmed records, closure remains unavailable. The recipient's confirmation acknowledges a record in TallyNest; it does not verify a bank transfer.

Any cycle member may create an expense while open or propose a settlement as sender while frozen; only the intended recipient may confirm/reject. The group owner alone may explicitly freeze, close, or open a next cycle. Existing creator/owner expense-edit permissions and group authorization remain. All transitions require authentication, CSRF/Origin protection, group membership, a current ETag/`If-Match`, and an idempotency UUID. The owner must remain an authoritative current member. No owner transfer is introduced here.

## 4. Per-cycle financial invariants

For each live expense in cycle `C`, `amountMinor` is a positive safe integer, its positive participant shares sum _exactly_ to the amount, and its payer/participants belong to `C.memberIds`. Tombstones remain integrity-checked and attributed to `C` but are excluded from paid/share totals. For member `i`:

```text
net(C,i) = paid(C,i) - assigned(C,i)
         + confirmedSent(C,i) - confirmedReceived(C,i)
```

Only confirmed settlements affect `net`. Pending settlements reserve sender debt and recipient credit for proposal capacity; rejected settlements reserve nothing. Sum of paid equals sum of assigned, sum of confirmed sent equals sum of confirmed received, and the sum of all net balances is exactly zero. Suggestions use the existing deterministic ID-tiebroken greedy algorithm on _one cycle_ and are never automatic settlement records. A new cycle starts with all-zero financial positions, regardless of the preceding cycle's activity; preceding closure must already have reached zero.

Run MongoDB aggregation matched by group **and cycle** and validate every record, including corrupted or unsafe values. Use `BigInt` for intermediate arithmetic and convert to JSON numbers only after individual fields and totals pass `Number.isSafeInteger` bounds. Never sum currencies together. If a required value is invalid or a total overflows, fail closed with a sanitized error; do not return a partial balance or allow closure. Group-wide historical reporting must aggregate each expense/settlement once by its immutable cycle ID, keep its own safe-integer limits, and never call a group obligation a bank balance.

## 5. Standalone MongoDB concurrency and recovery

**Serialization boundary.** All financial mutations and cycle transitions acquire the single `Group.financialOperation` slot with an atomic group-version CAS. The predicate includes authenticated membership, `financialProtocolVersion`, `currentCycleId`, `cycleEpoch`, mirrored state, and the absence of another reservation. Expense writes additionally require `open`; settlement writes require `frozen` (the first proposal performs the freeze under its own reservation). The target-document CAS includes its immutable group/cycle association, expected document version, and fixed operation receipt. A MongoDB write to an expense cannot directly predicate on fields in the separate group document: safety depends on advancing the group reservation to `applying` before that write and never releasing it until the intended effect is proven. A mere read of cycle status before writing would recreate the current race and is forbidden.

**Two phases.** `checking` permits validation and balance/capacity checks without external writes. If it fails, a CAS may clear it only while it is still `checking`. Before the first cross-document effect, CAS the same reservation to `applying`, fixing all payload values and target IDs. An `applying` reservation may be completed or reconciled, never silently discarded because of an error or timeout. Subsequent requests get `FINANCIAL_BUSY`. Recovery is bounded, actor/owner-authorized, and repeats the fixed intent; it does not invent a new target or use a newly selected cycle. Majority-acknowledged, journaled writes retain the current durability policy (`backend/src/utils/durable-write.js`), while still not claiming cross-document atomicity.

**First proposal/freeze.** Reserve a fixed settlement-create intent against open cycle/epoch. Recheck member snapshot, recipient, exact cycle capacity and document versions under the reservation. Mark applying; CAS cycle `open → frozen`, writing `freezeOperationId` and `frozenAt`; CAS the group's mirrored state to frozen, setting `settlementStartedAt` only if not already set; insert the pending settlement with fixed `_id`, cycle ID, original key/hash, and operation receipt; release only after the record or an equivalent receipt is observed. If insertion fails after freeze, recovery either completes the same proposal or reports a durable frozen cycle needing intervention; it never silently reopens. Future explicit freeze follows the same ordered state/receipt protocol without insertion.

**Recipient decision.** Reserve in the same cycle/epoch, revalidate pending status, recipient, version, and capacity where the present protocol requires it, then CAS `pending → confirmed/rejected` with decision operation receipt. Reconcile the receipt before releasing. A repeated confirmation reports the existing outcome; it never applies a second balance effect.

**Close.** Preflight balance and pending count, reserve the exact frozen cycle and epoch, reaggregate _under_ the reservation, and verify zero balances, no pending records, no corruption, and no other operation. Mark applying. CAS cycle `frozen → closed` with fixed close receipt, close totals/digest, `closedAt`, and removal of `activeSlot`; CAS group mirror to closed while retaining pointer to the last closed cycle; release. Group financial writes remain blocked throughout. A failed post-reservation check clears a checking reservation, not an applying one.

**Open next.** Reserve against a closed group pointer/epoch with an owner-chosen UUID, fixed new ObjectId, next sequence, and sorted member snapshot. Mark applying. Insert the open cycle; the unique active-slot and `(group,sequence)` indexes reject split-brain creation. CAS group pointer/state/epoch to that exact cycle, then release. A crash after insertion leaves the group busy until recovery attaches the _same_ cycle. No expense may target it before pointer commit. Do not combine close and open into one optimistic request.

**First-cycle bootstrap.** A group with no history and no cycle reserves its first financial create with a fixed cycle-1 ID, sequence, epoch and member snapshot. In `applying`, it inserts the open cycle, installs the group pointer/state, establishes `financialHistoryAt` before an expense becomes visible, and only then executes the fixed create. The same operation receipt recovers a crash at each boundary. A failed create may conservatively retain the permanent history marker, as the current protocol already permits; it must not leave a second active cycle. An owner may instead explicitly open an empty first cycle using the same transition steps. The first settlement proposal cannot bootstrap an empty cycle without capacity, because no one owes anyone yet.

The group CAS and unique indexes serialize **application writers**, but there is no MongoDB multi-document transaction. Reads must check group reservation/version before and after aggregation, returning busy or retryable conflict on mismatch. This is a best-effort coherent view under protocol-compliant writers, not a database point-in-time snapshot against out-of-band writes. Operational privileges should prevent direct collection writes outside the application/migrator.

### Crash/retry cases to prove

| Interruption                                | Durable observation and recovery                                                                                                                                                                                                                             |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Before reservation                          | No effect; request may retry with same UUID.                                                                                                                                                                                                                 |
| Reservation in `checking` before effects    | Fixed intent is visible. Revalidate or CAS-cancel only if still checking; an old worker's checking→applying CAS then fails.                                                                                                                                  |
| After `applying` before first write         | Recover the fixed intent; do not free the slot on an ambiguous error.                                                                                                                                                                                        |
| Cycle frozen, group mirror still open       | Freeze receipt identifies the transition; recovery updates group mirror, then completes settlement insertion. Expense writers see a reservation and cannot enter.                                                                                            |
| Group mirror frozen, settlement absent      | Insert by fixed ID/key/hash or find receipt. A rejected/retried first proposal cannot reopen the cycle.                                                                                                                                                      |
| Settlement inserted before response/release | Find receipt, return replayed outcome, then release reservation.                                                                                                                                                                                             |
| Decision written before release             | `lastFinancialOperation` and terminal status identify completion; no second confirmation.                                                                                                                                                                    |
| Cycle closed before group mirror changes    | Close receipt and absent active slot drive the same pointer/state update. No new cycle can be opened through the busy group.                                                                                                                                 |
| New cycle inserted before pointer change    | Recover by fixed cycle ID; unique indexes bar a second active cycle.                                                                                                                                                                                         |
| Group pointer changed before release        | Same operation/epoch receipt permits release, not another cycle increment.                                                                                                                                                                                   |
| Old worker resumes after recovery           | All later CAS predicates include operation ID, phase, epoch and versions; old target retries are limited to the original cycle and cannot mutate a closed cycle. **Pre-upgrade binaries must be stopped before cutover** because they lack these predicates. |

Recovery must distinguish duplicate-key replay from mismatched payload, preserve the idempotency receipt, and escalate unexplained corruption for operator investigation instead of force-clearing the reservation. The availability trade-off is deliberate: one unresolved operation blocks that group's financial writes until explicit recovery. Do not add a lease that expires while an old writer may still be running.

## 6. API evolution and compatibility

Proposed cycle endpoints under existing group authentication, no-store caching and mutation protections:

| Endpoint                                           | Purpose                                                                                                 |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET /api/groups/:groupId/cycles?limit=&after=`    | Bounded, sequence-desc history; cursor binds group and sort.                                            |
| `GET /api/groups/:groupId/cycles/:cycleId`         | Member-only cycle metadata, version/ETag and status.                                                    |
| `POST /api/groups/:groupId/cycles`                 | Owner opens the first or next cycle; UUID `Idempotency-Key`, group `If-Match`; never implicitly closes. |
| `POST /api/groups/:groupId/cycles/:cycleId/freeze` | Owner explicit freeze; UUID key and cycle ETag.                                                         |
| `POST /api/groups/:groupId/cycles/:cycleId/close`  | Owner zero-balance close; UUID key and cycle ETag.                                                      |

Cycle IDs are ObjectIds but public IDs are treated as opaque. Existing 428 missing `If-Match`, 412 stale precondition, 409 financial conflict/busy, 404 inaccessible object, and sanitized validation errors remain. An idempotent transition replay returns the prior transition result; same key/different normalized payload is 409. Transition receipts and uniqueness are scoped to group, actor, operation kind, and key; operation IDs themselves are unique and immutable. No caller may select an owner, member snapshot, epoch, or version in a JSON body.

Existing expense and settlement **read** routes can accept optional validated `cycleId`. Omitted `cycleId` keeps the historical group-wide listing/lookup/balance meaning during compatibility; cycle-specific views use explicit IDs and group-scoped authorization. `GET /balances?cycleId=...` returns that cycle's paid, assigned, confirmed, pending, net and suggestions; an additional explicit group-history summary can be added if needed. Old response envelopes and DTO fields remain unchanged until clients are upgraded. After coordinated frontend release, cycle-scoped response DTOs add `cycleId` and cycle state. This matters because the current frontend expense Zod schema is strict. Group-wide lists keep their current stable date/ID or ID sorting; cycle lists use the same keys with a cursor bound to group, cycle, and sort. A cursor from one cycle must be rejected for another. Pagination remains bounded and cannot silently skip to a new current cycle.

For **new mutations**, an explicit `cycleId` in the validated request is required once a group has more than one cycle. Expense update/delete and settlement decision target the immutable cycle on the retrieved record; an optional submitted cycle ID must match. New creation hashes include the explicit cycle ID. Look up an existing idempotency receipt **before** resolving a default cycle, so a lost-response retry after close returns the original resource or tombstone outcome. Preserve legacy creation hashes and group-wide key indexes; never re-hash an old receipt using today's current cycle.

To keep old clients safe, an omitted cycle on existing creation routes binds only to the group's first/legacy cycle while it is open/frozen as appropriate. Once that cycle closes, return a documented 409 `CYCLE_SELECTION_REQUIRED`; never default an old retry or an old frontend to a later writable cycle. A new group can lazily establish cycle 1 under the group reservation at its first financial write, preserving the old create flow. Explicit `cycleId` is required to work in cycle 2+. This is a deliberate usability trade-off until the frontend ships. The old mutation response shapes remain intact for legacy requests. No migration or deployment may silently make an old browser capable of creating a financial entry in a different cycle.

`POST /api/groups/:id/financial-recovery` remains a one-operation, actor/owner-authorized action. It returns sanitized kind/phase/cycle metadata and authoritative completion or busy status, not a force-unlock facility. A successful recovery refreshes group, cycle, expense, settlement, and balance state. Existing ETags use the current `tn-<id>-v<version>` convention for each document; group/cycle transitions use their own current versions. Creation keys are not reused across cycles, even for otherwise identical expense details.

## 7. Legacy migration and release cutover

**Recommended: offline maintenance migration.** Announce a maintenance window; stop all API instances, periodic workers and old financial-recovery workers; take and verify a restorable Atlas/local backup; then run a versioned, restartable migrator with maintenance-only database credentials. Capture counts, IDs, indexes, checksums/reconciliation output, and backup identifier without logging secrets. Recover existing `financialOperation` reservations with the old fixed payload first. Quarantine any operation that cannot be deterministically reconciled. Do not activate cycles for that group until resolved. Run compatibility validators that temporarily permit both old and backfilled records; install strict new validators and indexes only after verification. Start only new binaries after the full cutover. This is simpler and safer than concurrent dual writers on standalone MongoDB.

For each group, store a migration phase, fixed legacy cycle ID, and source checkpoint under a versioned group reservation. Groups without any financial history remain cycle-less until first write. For groups with history, create sequence 1 with immutable currency and member snapshot reconstructed from current embedded membership and historical payer/participant IDs; fail closed if IDs cannot be reconciled. If `settlementStartedAt` exists, its cycle is **frozen**, never open. Otherwise a history-bearing cycle is open. Backfill `cycleId` into every expense (including tombstones) and settlement, preserving their `_id`, `__v`, creation keys/hashes, operation receipts, dates, and statuses. Existing personal transaction records are untouched. Preserve `financialHistoryAt` and earliest `settlementStartedAt` exactly. Compare pre/post document counts, unique key sets, expense paid/share totals, confirmed/pending settlement totals, all member balances, and safe-integer boundaries. Then set the group pointer/epoch/protocolVersion by CAS and release the migration reservation. Each phase is restartable using the same fixed cycle ID and receipt; a partial backfill leaves the group unavailable, not half-enabled.

An unresolved pending reservation cannot simply be assigned to a cycle using its current group state: finish the old operation first or quarantine it. Likewise, tombstones and idempotency receipts are backfilled, not dropped. If a historical user is no longer in current membership or data is corrupt, produce an exception report and block cutover for that group. A frozen group with nonzero balances remains frozen after migration; it can close only via the new zero-balance rule. Migration itself must never make its old expenses writable.

**Alternative: online per-group dual protocol.** Install compatibility readers and writers, gate each group, migrate it in phases while other groups remain live, and reject old binaries via a database protocol-version predicate. It reduces downtime but requires two financial-operation implementations and race-proof routing for invitations, expense writes, settlements and recovery. A process that read the old group state before a per-group flip could still write unless every old write predicate is fenced. This is disproportionate for the initial cycle release; do not use it without separate proof and real MongoDB stress testing.

Rollback is safe before new-cycle writes only after checking the backup and restoring old binary/validator compatibility, while retaining every pre-cutover receipt. After a cycle-2 write, restoring an earlier backup would discard financial history; use forward recovery or a separately reviewed data repair, not blind rollback. Keep old workers shut down throughout. Do **not** run this migration as part of Step 3A.

## 8. Membership, corrections, performance and security

The permanent `financialHistoryAt` lock continues to forbid member removal and voluntary leaving, even after a cycle reaches zero. This is conservative and preserves historical attribution. Do not interpret a closed cycle as permission to delete its payer/beneficiary identities. Invitation joining should be allowed only before first financial activity or in the _closed-between-cycles_ window, with an atomic group-state/no-operation/version predicate. The new cycle snapshots the roster. No join during open/frozen activity; current-cycle shares and pending settlement recipients remain stable. Existing invitations must be revalidated at acceptance against this predicate. If that change is not shipped with cycles, retain the stricter existing admission behavior rather than silently altering a roster mid-cycle.

Former-member history access, member departure with settled obligations, owner succession, and missing/deleted user accounts require separate retention and authorization policy. Initially retain current group permissions and owner identity; do not add departure/transfer. Historical expense attribution uses immutable user IDs, not display names. Missing user profiles must not make financial records disappear; render a neutral identifier where authorized.

Confirmed settlements are append-only. An eventual correction system could add a linked reversal or adjustment record in a later cycle, with balanced debit/credit effects and explicit authorization, never mutate a closed expense or confirmed settlement. That design needs its own capacity, audit and anti-double-counting review; it is not part of the first cycle milestone. No direct edits to closed cycles are proposed.

Cycle-scoped aggregation and pagination use the proposed compound indexes. Keep group-wide history bounded; do not fetch all records into Node. Atlas M0 constraints favor a few access-pattern indexes and bounded result sets, not per-filter index combinations, caches, queues or change streams. Close/recovery aggregation may be slower for very large cycles; cap pagination and enforce request timeouts without treating a timeout as proof no write occurred. Detect unsafe totals rather than rounding or returning Infinity.

Every route retains JWT cookie authentication, CSRF and Origin checks on mutations, authenticated membership at the database write, owner-only lifecycle transitions, no-store financial responses, strict Zod inputs, and sanitized errors. Cycle IDs do not grant access across groups; every query is group-scoped. No personal transaction, budget or recurring record is created from a group cycle or settlement. There are no bank transfers, paid services, or automatic proof of payment.

The order deliberately keeps the new behavior disabled until the write protocol and migration are verified. A backend feature flag or protocol version must fail closed; merely hiding UI controls is not a release gate.

## 11. Decisions for review before implementation

1. **Maintenance window:** approve offline backup, old-worker shutdown and staged validator/index deployment rather than live dual-protocol migration.
2. **Old-client rule:** approve first-cycle-only default and `CYCLE_SELECTION_REQUIRED` after closure. This sacrifices old-client cycle-2 creation to avoid ambiguous retries.
3. **Owner explicit freeze:** approve it so a zero-expense cycle can close; it is irreversible and needs a clear confirmation UX.
4. **Pending withdrawal:** defer. Pending proposals must be confirmed or rejected before close; frozen status remains even after rejection.
5. **Membership:** approve join only between cycles and retain the permanent removal/leave lock until a dedicated historical-obligation policy exists.
6. **Correction records:** defer append-only reversal/adjustment design; never reopen or directly edit a closed cycle.
7. **Operational recovery:** approve durable busy states rather than automatic lease expiry. Define an operator escalation path for irreconcilable corruption without granting a force-unlock API.

No implementation, database change, or migration is authorized by this document alone.
