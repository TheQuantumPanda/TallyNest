# Phase 5, Step 3I — post-migration release preflight

**Decision: NO-GO for public cycles.** This milestone adds read-only inspection of a synthetic, maintenance-held migration rehearsal. It does not release a marker, migrate real data, register staged routes in the normal server, or enable the cycle frontend in the normal build.

## Validator mismatch and resolution

The Step 3E migrator installs `strictGroupValidator(base, strictGroups)` on `groups` and `strictFinancialValidator(base, strictGroups)` on `groupexpenses` and `groupsettlements`. Step 3F readiness previously compared all five validators only to their base definitions. A correctly migrated database therefore looked like schema drift. The new `verifiedMigrationManifest` derives the exact ObjectId group set from the single version-1 run, its completed phase-8 checkpoints, and the actual sorted group set. It rejects missing, extra, unsorted, duplicated or inconsistent IDs and incomplete or quarantined checkpoints before using that set to reconstruct the expected strict definitions. `verifyCycleSchemaAndIndexes` then compares canonical BSON structures and exact `validationLevel: strict` / `validationAction: error`. Base definitions remain required where no completed run exists. The two cycle and transition validators remain exact base definitions. The migrator's marker-collection validators are exported from their existing builder and checked exactly; no validator is relaxed or installed by this preflight.

Required model indexes are checked for key order, uniqueness, sparseness, partial filter and collation. Missing indexes, unexpected unique/partial indexes, and any TTL index on these financial or marker collections fail. This includes the group-wide expense and settlement creation-receipt unique indexes, active-cycle partial unique slot, cycle sequence/history, and transition-journal unique receipt index. Ordinary extra nonunique, nonpartial indexes are not treated as a financial integrity failure. This check reads MongoDB metadata; it does not call `createIndex` or `collMod`.

The staged `assertCycleHttpReadiness` uses the same schema/index checker. Its existing maintenance rejection remains first, so a held migrated database is still unavailable to HTTP. A post-migration schema PASS is **not** authorization to serve it. The ordinary Express app and frontend continue to use legacy contracts.

## Read-only interfaces and report

`assessCycleReleasePreflight(connection)` returns a sanitized JSON object with overall `status`, `checks`, and `metrics`. Check states are `PASS`, `FAIL`, `BLOCKED`, or `NOT_VERIFIED`. The checks cover migration checkpoints/reconciliation, schema, indexes, group/cycle associations, active financial reservations, maintenance, independent backup/restore evidence, old-writer fencing, deployed version compatibility, runtime privileges, and operational release eligibility. A mandatory FAIL makes the overall result FAIL; otherwise held maintenance or the absent release mechanism keeps it BLOCKED. It never reports GO on database inspection alone. The report contains codes, counts and timing only, not notes, account data, token hashes, fixed operation payloads or secrets.

The inspector requires a Mongoose connection with `autoIndex: false` and `autoCreate: false` before it registers the read models. The executable entry point creates such a connection itself and accepts **only** a locally generated `tallynest_cycle_rehearsal_<13-digit timestamp>_<12 hex>` database:

```bash
npm run preflight:cycles:rehearsal --prefix backend -- \
  --database tallynest_cycle_rehearsal_<timestamp>_<suffix>
```

The placeholders must be replaced with the exact disposable name. The CLI does not accept an arbitrary URI or credentials. It prints JSON and exits 2 for the expected maintenance BLOCKED result, 1 for FAIL/inspection failure. It never updates data or releases a hold. A future real-data preflight requires a separate reviewed operator interface; renaming a real database to match the disposable pattern is prohibited.

For each completed checkpoint the assessment verifies the original immutable group identity and version digest; maintenance provenance; Cycle 1 ID, sequence, currency, member snapshot, state and marker order; current pointer and epoch; and exact cycle association of active expenses, tombstones and every settlement status. It runs the existing `reconcile` calculation against the stored pre-migration snapshot, including creation keys, versions, receipts, exact paise totals, member identities, zero-sum balances and deleted-entry evidence. An unresolved `financialOperation` blocks reconciliation rather than being cleared. No financial write or repair is attempted.

## Disposable restore and negative tests

`backend/integration/cycle-release-preflight.mongo.js` creates registered synthetic users and six legacy groups: empty, open, frozen with confirmed settlement, frozen with pending settlement, frozen with rejected settlement, and a group with a deleted-expense tombstone. It performs the existing encrypted backup/restore rehearsal and migrates only the generated database. The positive test compares the full database and schema digests before and after both the library and CLI inspections. It observes schema/index/association/reconciliation/reservation PASS, maintenance BLOCKED, and no collection, document, index or marker change. Frozen Cycle 1 records stay frozen; the original history markers, settlement statuses and tombstone receipt are compared by `reconcile`.

Isolated negative cases deliberately alter only that disposable fixture, call the read-only inspector, then restore the fixture and verify a clean assessment: weakened expense validator; unexpected migration-marker validator; missing group-wide receipt index; duplicate creation receipt after that index is removed; wrong active-slot partial filter; missing transition-journal index; unexpected financial-receipt TTL; incomplete checkpoint; tampered strict group set; removed expense `cycleId`; wrong epoch, pointer or state mirror; frozen cycle marked open; and an unresolved applying reservation. The tests do not use a real development or production database. Intentional raw corruption is test setup, never an action taken by the inspector.

## Performance and placement

An isolated local standalone MongoDB 8.0 run on six migrated groups measured one collection metadata probe, seven index probes, 0.80 ms metadata read, 1.93 ms validator comparison, 2.87 ms index inspection, 67.77 ms group/cycle association plus reconciliation, 53.49 ms within that for six exact financial reconciliations, and 76.50 ms total. The same fixture under the concurrently running clean suite measured 1.37 ms, 2.84 ms, 6.32 ms, 124.20 ms, 97.84 ms and 143.22 ms respectively. The full encrypted backup/migration fixture setup is outside those timings. These are local measurements, **not** Atlas M0 latency or a capacity prediction. Larger histories increase reconciliation cost.

Run the full manifest, schema, index, association and exact reconciliation assessment **offline during maintenance**, after migration and before any release decision. A future startup may use a read-only bounded schema/marker check under runtime credentials, but must fail closed on missing constraints or permission errors. Do not put full-history reconciliation on every HTTP request. Existing write-time CAS, membership checks, validator enforcement and fixed-intent recovery remain necessary; a prior preflight success cannot substitute for them or be cached across schema/protocol changes.

## Startup and privileges

Current `backend/server.js` first probes the database-wide hold, then calls `ensureUserIndexes`, `ensureBudgetIndexes`, `ensureRecurringIndexes`, `ensureGroupIndexes`, `ensureGroupFinancialCycleIndexes`, `ensureGroupExpenseIndexes`, and `ensureSettlementIndexes`. Those setup methods may create collections/indexes or call `collMod`; normal startup does **not** install the cycle-transition journal index. This is not a least-privilege version-2 startup. The new CLI only needs collection/document reads, `listCollections`, and `listIndexes`; exact financial reconciliation additionally reads financial collections. Migration/setup needs create-collection, create-index, `collMod`, and migration checkpoint writes. Backup/restore needs separately scoped dump/restore authority. Actual runtime Atlas roles and permission failures are not tested here. A future reviewed startup must separate schema installation from read-only readiness before reducing runtime privileges; this milestone does not switch startup.

## Browser and release gates

The disposable Chromium suite now exercises keyboard Enter/Escape and focus return for a lifecycle dialog, reduced-motion CSS, a keyboard navigation check under CDP 200% page scale, 320px no-overflow/usable form controls, and a one-time test-fixture interruption **after** an expense write. After a full reload discards the in-memory retry key, the owner explicitly recovers the fixed applying reservation and sees the persisted expense once. The fault hook lives only in `backend/integration/cycle-ui-server.js`; no production route or browser flag enables it. CDP page scale is a limited zoom proxy, not an assistive-technology audit. The fixture now disconnects Mongoose before dropping its exact disposable namespace through a raw client, and the browser runner checks twice after child-process exit with a longer delay. Two other local disposable namespaces predated this milestone's test runs and were deliberately not deleted; the runner only owns its newly generated namespace.

Before any future maintenance release, an operator still needs independently controlled encrypted backup/key custody and a successful restore proof; actual shutdown of every old API, recurring and recovery worker; revoked/fenced old write credentials and connection paths; completed checkpoints with no quarantine; approved strict validators and indexes; no unresolved financial operation; matching new backend/frontend contracts; least-privilege runtime startup; and hosted HTTPS cookie/Origin/CSRF validation. An operator statement alone cannot prove an old worker cannot reconnect. There is no approved marker-release mechanism or safe old-binary fencing implementation. Restoring a pre-cutover backup after new cycle writes could erase acknowledged financial history. No Atlas, hosted HTTPS, production backup, or public cutover was tested.

## Verification

`npm run verify:clean` passed: 314 backend unit/HTTP tests, 265 frontend tests, 256 real MongoDB integration tests (including 17 preflight tests with 15 drift subtests), backend/frontend/shared ESLint, configured Prettier, the production frontend build and both production dependency audits with zero reported vulnerabilities. The staged HTTP suite passed 23 tests after the readiness change. The Chromium suite passed 3 tests against disposable Express/MongoDB and confirmed cleanup of its generated database. Direct documentation formatting, targeted lifecycle/migration regressions and final cleanup are recorded in the handoff; this document is not a hosted release approval.

**Next review:** design a separate maintenance-release and new-binary-only least-privilege startup procedure, with independently verified old-writer fencing and backup custody. Do not activate cycles on the strength of this preflight alone.
