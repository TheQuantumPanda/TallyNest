# Phase 5, Step 3C — internal cycle-aware financial writes

**Status:** internal protocol and disposable-database verification only. No authenticated cycle lifecycle route, legacy migration, production activation, or frontend integration exists. Ordinary groups retain the legacy permanent settlement freeze.

## Boundary and design adjustment

The Step 3A design anticipated a versioned group reservation but did not account for two current-code details. Invitation acceptance could alter an embedded roster while a financial reservation was pending; its MongoDB write predicate now permits version-2 membership admission only in the closed-between-cycles state with no reservation. Its legacy predicate is unchanged. Legacy financial reservation and recovery also lacked a protocol-version fence; they now require an absent `financialProtocolVersion`. The existing public expense and settlement services reject version-2 fixture groups, including idempotent creation replays. This prevents a legacy fallback from interpreting a cycle-bound record as an ordinary group-wide write. None of these changes activates cycle behavior for ordinary users.

`createCycleFinancialService` is an internal factory that throws `CYCLE_PROTOCOL_INACTIVE` unless explicitly instantiated with `internalEnabled: true`. The production Express router never instantiates it and has no version-2 endpoint. Disposable MongoDB tests alone write group protocol fields directly. Optional cycle fields on legacy documents remain absent. A later migration and controlled cutover must stop old binaries before any real group is marked version 2.

## Reservation and atomic fencing

The existing single `Group.financialOperation` slot now optionally stores `protocolVersion: 2`, operation ID, kind, actor, group and cycle IDs, cycle epoch, expected group and cycle versions, fixed target ID, normalized payload, SHA-256 payload hash, initial cycle state, and phase (`checking` or `applying`). Legacy reservation documents retain their original shape. MongoDB collection validation checks version-2 field types, group/current-cycle association, epoch, and actor membership; Mongoose also validates the shape. The service verifies the entire immutable intent against the hash before applying or recovering. The hash detects accidental or unauthorized document alteration; it is not a MAC against a database administrator.

`reserveCycleFinancial` performs a single group-document compare-and-set requiring authenticated membership, protocol version 2, current cycle ID/epoch/state, expected group version, a permanent history marker, and an empty operation slot. The cycle record is then read and its group, currency, status, member snapshot, and expected version are checked. The checking phase performs split, source-version, membership, and settlement-capacity checks without writing an expense or settlement. On a deterministic validation conflict, a still-checking reservation may be cancelled. Otherwise the same operation ID atomically advances to applying. An applying reservation never expires and cannot be force-cleared. The fixed target ID, operation ID, epoch, payload and expected versions are reused during recovery.

The coordinator executes one group operation at a time. The group reservation predicates fence every compliant financial writer. Expense replacement/deletion and settlement decisions additionally use group/cycle/document-ID and document-version predicates. The cycle freeze uses cycle status/version and the fixed freeze operation ID. Collection validators enforce local record shape, not cross-document financial reconciliation; this still relies on all writers honoring the group reservation protocol. Out-of-band database writes are outside that guarantee.

## Expense and settlement effects

An open cycle accepts internal creation, replacement and tombstone deletion of its own expenses. Splits use the existing exact allocator and selected payer/participants must be both current group members and members of the immutable cycle snapshot. The expense repository writes immutable `cycleId` and preserves the existing group-wide creation-key index. A creation-key replay resolves its original receipt **before** selecting the current writable cycle. An edited record replays as the same record; a deleted receipt returns `EXPENSE_DELETED`. An old key cannot create a new-cycle expense. Existing personal finance collections are untouched.

The first capacity-valid settlement proposal starts in an open cycle. Once applying begins, the fixed operation freezes that cycle by versioned CAS, writes the group state mirror and earliest-ever `settlementStartedAt` marker, and inserts one fixed-ID pending settlement. A rejected proposal does not thaw the cycle. Later proposals, recipient-only confirmations, and rejections require a frozen cycle. They retain the existing group-wide creation-key uniqueness and settlement document-version checks. Pending capacity, confirmed net effects, and debt suggestions are computed only from the requested group/cycle. MongoDB aggregation matches both IDs before checking source integrity; deleted expense receipts are validated but excluded from totals. BigInt calculations and safe-number output checks remain in the shared balance utilities. The public group-wide balances endpoint is unchanged.

Cycle expense and settlement history indexes were added for future cycle-scoped reads: `{ group: 1, cycleId: 1, expenseDate: -1, _id: -1 }` and `{ group: 1, cycleId: 1, _id: -1 }`. Existing receipt uniqueness indexes are unchanged. No public cycle-scoped pagination API is exposed yet.

## Recovery and failures

The actor or group owner may call the **internal** recovery method. A checking reservation can be revalidated and promoted or cancelled on a definite conflict. Applying recovery checks the original cycle/epoch/operation ID and payload hash, then reconciles the fixed target document and its `lastFinancialOperation` receipt. The group slot releases only after that proof. Unknown or corrupt outcomes leave it busy for investigation, rather than risk a second effect. For first proposals, recovery recognizes the fixed freeze receipt before completing the group mirror and settlement insert. No timeout lease or fallback to a next cycle exists.

Fault-injection tests stop after reservation, checking, promotion, target insertion, cycle freeze, group mirror, and before release. Separate MongoDB clients test reservation contention, competing first proposals, expense update versus freeze, confirmation versus another proposal, and a delayed worker after recovery. These are injected stops and independent clients, **not** process-kill, network partition, primary failover, Atlas, or production-data verification. A permanently corrupt applying intent may require operator-led database investigation; this milestone intentionally has no force-unlock API.

## Activation prerequisites and limitations

Step 3C does not provide explicit freeze/close/open lifecycle operations, old-record backfill, migrated receipt association, public cycle-aware DTOs, or safe mixed-binary cutover. The test fixture's transition to Cycle 2 is direct disposable-database setup, not a lifecycle implementation. Future activation needs the Step 3A close/open and recovery protocol, full legacy migration/reconciliation, backup and old-worker shutdown, and a coordinated frontend/API contract. The permanent legacy `financialHistoryAt` and `settlementStartedAt` protections remain in place throughout this milestone.

Run the targeted real-database suite with `npm run test:mongo --prefix backend` (which includes `integration/cycle-financial-writes.mongo.js`) or run that file directly from `backend`. Tests create uniquely named disposable databases and drop them after completion. `npm run verify:clean` runs the complete local release gate. This document records the protocol and its tested boundaries; it does not claim that multi-cycle operation is ready to enable.
