# TallyNest — final predeployment verification

Date: 20 October 2026 (Asia/Kolkata). Runtime: Node.js 24.21.0, local MongoDB 8.0.32, bundled Chromium. Tested working tree: base commit `0f5dde1` plus the uncommitted changes described here. Scope: local fresh-v2 application and controlled deployment rehearsal readiness. All changes remain uncommitted. No deployment, real-data migration, production schema installation or persistent financial-record edits were performed.

## Decision

**GO for beginning a controlled, isolated fresh-v2 deployment rehearsal with generated data. NO-GO for public release, production cutover or real-data migration.** No local functional blocker remains after the fixes below. The rehearsal must use separately reviewed hosted fresh-schema provisioning and prove the hosted gates listed below; the disposable local installer is not a production installer. This report does not authorize deployment in this task.

## Composition and isolation

The normal browser launcher provisions a generated `tallynest_fresh_v2_test_<timestamp>_<random hex>` database, installs the existing fresh-v2 schema explicitly, and starts the actual `backend/server.js` on port 5500 and normal Vite/React entry on port 5173. It uses no staged Express composition, seeded accounts, repository substitutions or server fault hooks. Three independent browser contexts register their accounts through the normal registration form. The separate existing staged browser suite remains an additional regression gate.

MongoDB is the existing local `mongo:8.0` Docker service. Only generated databases belonging to each test harness are setup/dropped. The integration launcher runs the same 17 files as separate sequential Node test processes, each retaining `--test-concurrency=1`. Before/after each file it reads WiredTiger open-file and pending-drop metrics and waits for open-file headroom (at most baseline + 128, capped at 384), with a bounded 90-second wait and a one-connection observer. Integration gates and browser launchers run sequentially to respect the container's unchanged 2,048-descriptor limit. The launcher refuses missing metrics or insufficient initial headroom and never restarts MongoDB, changes limits, flushes storage or drops databases. Each launcher stops its own child services before verifying that its exact database has been removed. No manual container restart or limit change was performed, and no unrelated process/database was stopped or cleaned.

For one normal-server recovery drill, the browser test temporarily extends the **disposable database's** existing group validator to reject only removal of the tested group's financial reservation. Reserve, promote and expense insertion still use the actual production repositories. The write returns 500 after a durable expense exists, leaving an `applying` reservation. The original validator is restored in `finally`, before authorized HTTP recovery. No financial record, operation payload or application protocol is manually repaired. This is an external storage failure drill, not a process-kill claim; the existing lifecycle MongoDB suite separately tests actual SIGKILL recovery with independent OS workers.

## Local security/runtime verification

- Actual session cookies are HttpOnly, SameSite=Lax, host-only and path `/`; the normal browser cannot read them through `document.cookie`. Existing backend tests also verify production `__Host-sfm_access` Secure cookie construction/clearing. Local HTTP cannot prove hosted browser delivery of that production cookie.
- Normal-server requests reject a foreign Origin and a missing CSRF header with 403. Unit/HTTP coverage exercises missing/null Origin, invalid tokens, protected input and route authorization.
- Cycle, expense, settlement and recovery permissions, exact per-user rate limiting and no legacy financial fallback are exercised through the normal server. A fully valid legacy-shaped expense request that omits cycle selection returns 409 `CYCLE_SELECTION_REQUIRED`, persists no record and never invokes a legacy writer.
- Actual API financial responses use `Cache-Control: no-store`; normal browser coverage checks balances plus personal transaction, budget, recurring and cycle endpoints. Route tests cover the other response paths. Hosting/CDN behavior remains separate.
- The launcher captures normal server stdout/stderr through successful and failed requests and shutdown, and asserts absence of the generated password/signing secret, cookie assignments, password hashes, selected generated emails, JWT-shaped tokens and financial payload titles, while requiring a nonempty captured startup log. This is a bounded ordinary-log check, not a guarantee about future infrastructure logs or all possible values.
- Existing readiness tests validate schema/index/association/hold rejection without repair. Additional integration tests launch actual `server.js` against disposable legacy, validator-drifted and nonready setup profiles, require exit 1 before listening, and compare collection definitions, indexes and records before/after. The existing uninitialized startup test also proves no collections are created.
- Unresolved operations fail closed for the affected group's balances and ordinary writes, remain reserved and require actor/owner recovery. No timeout unlock, force-clear or alternate legacy writer is introduced. Existing MongoDB tests cover corrupt payload quarantine, safe-integer boundaries, concurrent workers and immutable historical associations.

## Defects and changes

No financial-integrity defect was found. Visual review confirmed one small presentation defect: a later joiner viewing restricted historical balances saw both the correct snapshot-restriction notice and an unrelated stale-record/retained-draft warning with a reload action. `CycleWorkspace.jsx` now suppresses generic conflict feedback only for `CYCLE_MEMBERSHIP_CHANGED`, leaving the specific informational notice and all genuine stale/conflict feedback intact. The normal browser regression asserts that the misleading warning/reload action are absent while the API still denies the historical balance. This does not change permissions, financial calculations or recovery.

A repeated integration run also confirmed a test-runtime reliability problem: dropped database/index files can remain open asynchronously in WiredTiger, so serial test execution alone did not prevent descriptor exhaustion after repeated gates. MongoDB logged `TooManyFilesOpen` while only nine connections were observed, then automatically restarted once. The affected run failed in settlement setup with a lost MongoDB connection; its stuck owned worker was stopped and its exact generated database, identified in the storage log, was removed. The container was not manually restarted and its 2,048 limit was not changed. The new `run-mongo-tests.js` resource guard and `test:mongo` script wiring wait for headroom between the same suites. This is test orchestration, not a financial protocol change. Evidence: `output/predeployment-verify-descriptor-failure.log` and `output/predeployment-mongo-descriptor.log`.

Changes are limited to that display condition, normal browser coverage/launcher, actual-server startup integration regressions, the serial MongoDB resource guard/script wiring and this report. No backend production source, dependency, schema definition or financial protocol changed. Both complete verification runs and the combined browser gate passed after the display and test-runner fixes.

Initial test development corrected expectations to the contract's 412 for stale ETags and 409 `CYCLE_SELECTION_REQUIRED` for otherwise-valid input lacking a cycle. History assertions follow the documented distinction between snapshot-restricted balances and current-member-readable expense/settlement records. An early verification attempt encountered an in-flight runner formatting edit; it was corrected with the repository's Prettier configuration before complete reruns. These are verification development issues, not application fixes.

## Hosted checks and remaining deployment blockers

A controlled rehearsal must use a new isolated deployment environment and generated data. This local verification does not authorize real-data migration or public release.

Before a hosted release, evidence is still required for:

1. Actual HTTPS/Secure host cookie behavior, SameSite across the chosen frontend/API sites, CORS/CSRF, logout, session restoration and expiry through the real TLS terminator.
2. Exact reverse-proxy trust/client-IP behavior, multi-instance shared rate-limit storage or an explicitly constrained single-instance rehearsal, infrastructure request/body/cookie log redaction, and CDN/proxy `no-store` behavior.
3. Production build `/api` forwarding, exact production Origin and SPA deep-link/hard-reload routing.
4. Target MongoDB privileges and read-only readiness under runtime credentials; reviewed fresh-install operator tooling. The checked-in installer intentionally accepts only disposable local database names. There is no supported real legacy migration/maintenance release path.
5. Independent hosted backup, encrypted restore/reconciliation proof, recovery access and an operational rollback/recovery runbook tested against disposable hosted data. Local encrypted MongoDB backup/restore tests do not establish hosted backup readiness.
6. Manual toolbar zoom interaction and keyboard/assistive-technology checks on the hosted build; target browser/device smoke checks. Native 200% Chromium zoom and actual form submission are automated locally.

Current design limits remain: logout does not revoke copied JWTs before expiry, rate counters are process-local and reset on restart, privileged raw database writes can bypass application immutability, and trusted-origin script compromise is outside the CSRF defense. No paid service was introduced.
